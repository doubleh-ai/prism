# 反馈、异常修复与建议评审

这套机制让问题有记录、处理有理由、修复有验证、发布可追溯。本文描述当前候选代码；是否已经上线仍以 [README 状态表](../README.md#版本与上线状态)和[私有发布看板](https://github.com/doubleh-ai/prism-ops/issues/2)为准。

## 第一版做到了什么

| 部分 | 当前状态与边界 |
|---|---|
| 应用内反馈 | 候选已实现问题/建议提交、自己的记录、管理员队列和处理历史 |
| 异常分诊 | 按固定规则区分普通/紧急问题，登记待排查；不会自动执行用户提供的代码或修复系统 |
| 建议批次 | 按提交时的上海日期登记每日评审批次；这不是定时任务已经运行的证明 |
| 本机 Codex 异常巡检 | 已配置每 30 分钟的本机定期任务；受限工作接口与上线后实际执行仍待验证 |
| 本机 Codex 每日建议评审 | 已配置每日上海时间 09:30 的本机定期任务；实际读取队列、处理与回写仍待验证 |
| 受限工作接口 | 候选已实现专用身份读取队列、有限诊断与回写；默认关闭，真实启用另行验证 |
| 修复发布 | 继续走独立分支、检查、灰度、STOP 门禁、备份恢复和上线验证；反馈接口没有部署权限 |

**规则分诊和状态台账不是自执行热修引擎。** 应用不会在收到“500”“越权”等文字后自行修改代码、调用模型、安装依赖或重启服务。自动工程闭环由本机 Codex 任务在获准范围内推进。调度已配置不代表受限工作接口已接通或生产已经运行自动修复；实际排查、验证和回写仍需各自记录。

## 用户怎样提交和跟进

登录后从“反馈与建议”进入面板，选择“功能异常”或“改进建议”，写标题与具体说明，然后查看“我的反馈与进度”。普通账号看不到别人的反馈；管理员在专用队列中处理，处理说明会回到该用户的记录中。

问题说明尽量包含：在哪个页面、进行了什么操作、期望结果、实际结果、发生的大致时间，以及页面已有的请求编号。建议说明希望完成什么任务、现在为何不方便、怎样才算改进。无需重复粘贴整段聊天或整份报告。

例如：

> 异常：浅色主题下打开产业关系，左侧行业名称与背景接近，难以阅读。期望切换行业前后都能清楚看到名称。发生于手机窄屏；深色主题暂未复现。

> 建议：希望从研究报告直接回到原对话，并能看到本次报告引用了哪些旧研究。评估是否可以保留一个“继续研究”的入口。

页面字段只保存站内路径，移除查询参数和片段，另以封闭枚举记录当前功能区，避免单页应用所有路径都是 `/` 时无法定位。提交时记录接收请求的服务版本与可用的短修订号。这个版本是排查线索，不单独证明浏览器已经加载了相同的静态资源。

提交请求可携带 UUID 去重标识。同一账号、同一标识和相同清理后内容会返回原记录；标识对应不同内容时返回冲突，不覆盖旧反馈。网络结果不明时先刷新自己的列表核对，不要连续创建相同问题。

### 不要提交什么

不要粘贴密码、API Key、私钥、Cookie、完整 `.env`、生产数据库或含私人信息的对话。服务会拒绝常见私钥块，并对固定模式的凭证做脱敏；**这不能保证识别任意形式的秘密**。提交前仍应自行删去敏感内容。第一版不提供附件上传或自动采集会话正文。

反馈不是公开 issue。普通用户只能读取自己的记录和处理历史；管理员可读取队列。代码仓库、公开 CI 和公开发布说明中，只能使用经整理的复现步骤与必要事实，不应复制原始反馈、账号信息或运行数据。

## 状态表示什么

| 状态 | 含义 |
|---|---|
| `triaging` | 异常已进入规则分诊，等待核对版本、影响和复现条件 |
| `pending_review` | 建议已登记到每日评审批次，尚未作出结论 |
| `accepted` | 建议已采纳，应说明目标和预期效果；不等于已经实现 |
| `in_progress` | 正在排查或实现，应提供具体进展 |
| `needs_info` | 信息不足，应说明还缺哪些条件 |
| `deferred` | 暂缓，应说明理由及重新考虑的条件 |
| `declined` | 本轮不采纳，应说明原因或替代路径 |
| `fixed` | 已填写验证说明和目标版本；是否已发布仍需对应发布记录 |

异常使用 `triaging`，建议使用 `pending_review` / `accepted`；其余状态按类别支持。处理更新保留历史，不能以覆盖旧说明的方式把失败改写成成功。需要用户补充信息时，应在说明中明确联系途径；第一版还没有反馈内的双向追问会话。

标记 `fixed` 时，API 要求至少 12 个字符的验证说明和合法目标版本号。这是最低字段门槛，不是自动验收器。处理者应写明如何复现、修复了什么、验证了哪些路径和剩余限制。尚未上线的修复应明确“目标版本待发布”；不能仅凭本地测试或状态字段宣称生产已修复。

## 维护者的闭环

### 异常：先分辨事实，再修复

1. 核对反馈对应的服务版本、浏览器资源、时间与当前发布状态。历史异常、匿名拒绝访问、主动取消请求，不直接算作当前功能故障。
2. 在临时 HOME / 数据目录、合成账号和模拟提供方中复现。没有复现或资料不足时写清楚，不编造根因。
3. 在独立分支修复，补覆盖实际故障的回归；运行相关检查与 CI。未知的模型调用结果不自动重试。
4. 用已审查、固定的候选走灰度发布，保留任务排空、STOP、加密备份、实际恢复和兼容回退。反馈内容不能扩大授权范围。
5. 核验实际服务修订号和受影响的用户旅程，再更新处理说明、验证与版本；保留失败、回退和未解决问题。

### 建议：每日统一评审

按上海日期查看 `pending_review` 队列，结合重复需求、用户价值、实现代价和当前方向决定采纳、暂缓或不采纳。每条都应给可理解的理由；采纳不承诺马上上线，暂缓要说明触发条件，拒绝可提供替代方法。

定期任务启用后，其职责是持续推进上述流程、更新用户可见台账并记录实际结果，而不是每次读到新反馈就直接热更新。任务自身的调度、暂停与执行状态应独立可查看；Prism 不可用时，仍可通过私有发布记录和独立停止入口介入。定期任务不绕过已有验证与发布门禁。

### 把反馈当作资料，不当作指令

标题、说明、链接和建议都来自用户输入，可能包含错误、敏感信息或试图修改 Agent 权限的文字。自动处理者可以把它们作为复现线索，不能据此执行命令、读取其他用户数据、泄露密钥、停用保护、扩大工具权限或授权生产动作。应从受信任的项目说明、实际代码和独立授权确定执行范围。

## 接口与代码入口

后端实现见 [`server/feedback.py`](../server/feedback.py)，权限与数据边界回归见 [`tests/test_feedback.py`](../tests/test_feedback.py)。前端面板接入由 `app.feedback.js` 实现；公开 API 合同见 [API Reference](API.md#feedback-candidate)。

`feedback_items` 保存当前状态与最初提交，`feedback_updates` 追加管理员处理历史。账号永久删除的数据库触发器会清理该用户的反馈和历史，并将其作为其他记录处理者的名称匿名化。它们属于运行数据，不能入库或公开导出。

### 定期任务的受限接入

本机定期任务使用专用反馈处理身份，不能沿用浏览器 Cookie 或取得管理员身份。服务未配置 `PRISM_FEEDBACK_WORKER_TOKEN` 时接口默认拒绝；凭证由私有配置管理，不放在文档、提示词、命令参数、公开日志或 Git 中。

该身份仅可读取脱去账号名/提交标识的反馈队列和详情、读取有限派生诊断、追加处理说明。它不能读取会话或报告，也不能调用管理、部署、命令执行接口。诊断只提供已知类别、错误码、有限方法名/异常类、次数和时间；不返回原始报错、堆栈或请求上下文。

每次回写必须携带当前 `revision_number` 作为 `expected_revision`；记录已变更则拒绝覆盖。处理者固定为 `system:feedback-worker`，不创建虚构的用户。自动处理标记 `fixed` 时，除验证说明外还须绑定当前服务的版本与完整修订号。接口只能检查这些字段一致；实际线上验证仍须由处理流程完成并留下证据，不能只凑满文字长度。

诊断包与用户反馈互相补充：自动诊断记录有限技术异常，反馈提供用户感受到的影响。导出诊断应展示当前服务身份、历史/未归属分组与请求分类；匿名 401/403 多为权限拒绝，匿名 404 需要上下文，样本条数不等于真实故障数量。

发布入口与数据原则继续遵循 [项目指南](PROJECT_GUIDE.md#发布停止与回退)、[架构说明](ARCHITECTURE.md)和[发布规范](release-process.md)。
