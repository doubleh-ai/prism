# 发布观察与后续上线流程

## 本分支：有限恢复候选

`v0.19.8-recovery` 从公开历史 `e1b2ace7be87e27ab99a3e62368f7682cebd94f0` 保留旧界面和基线回归，新增固定入口 `server.recovery:app`。恢复执行器必须核对该入口与完整候选 SHA；`server.main:app` 没有恢复边界，不得用于恢复服务。入口没有允许绕过限制的环境变量。

允许已有账号登录/退出，读取本人数据库对话、已保存 JSON 报告、分析/Vibe 历史、自选和行情。所有 API 非 GET/HEAD（仅 POST 登录/退出例外）统一返回 503“恢复模式，暂不支持新研究”；未知写入路由也受限制。共享 HTML/PDF 文件、外部 CLI 档案、聊天流、扫描和内部工具桥不注册。读取旧 Vibe 任务不会重新启动；旧未完成状态只在响应中标记中断，不覆盖历史数据。恢复页面和响应均标记有限模式。

数据库只使用向前兼容增量及已退休账号保护，现有用户不替换、孤立历史不认领、不降级数据库、不恢复备份覆盖新数据。候选排除旧全局 SSL 校验绕过脚本，使用受控发布环境中的哈希依赖锁；锁不覆盖全部继承的外部 Astock 依赖，仍需独立清单。旧基线测试完整保留，新测试实际请求恢复入口并运行浏览器脚本验证。冻结后仍须单独完成 Linux 隔离副本启动、登录/归属/拒写和真实版本验收，不能把本地通过当作生产已恢复。

下文记录公开基线自带的候选流程；本分支不自带生产执行器，也不替代主发布分支受控执行器及其真实阶段记录。

当前阶段只准备候选版本（candidate-only），不接入生产写入。管理员看到的 GitHub 检查结果、本实例健康状态和生产发布状态必须分别理解。候选通过检查，不代表已经上线；本实例能访问数据库，也不代表它就是生产实例。

## 当前已提供的能力

- 管理员发布观察页从真实 GitHub 工作流读取状态、修订号与原始页面链接，并显示观察时间。结果可缓存 180 秒；读取失败、过期和未知状态不会自动变成“成功”。
- CI 与候选流程是检查和准备环节，不能当作部署记录。当前控制台不能执行生产发布、重启、停止远端发布或回滚。
- `/health/ready` 公开提供基础数据库就绪检查，200 表示检查通过，503 表示未通过。返回范围限于 `status`、`version`、`deployed_revision`、`checked_at` 和 `tz`。无法确认的版本或完整修订号显示 `unknown`。
- 管理健康页检查数据库、CLI 版本和研究方法是否存在。默认内置方法 `prism-research` 是必要项，缺失可选旧方法不再使总体状态失败。该检查不向真实模型或行情服务发请求。

生产尚未接入这一发布流程。本实例的版本元数据是本实例的声明，不是生产核验结果。当前页面不能声称覆盖所有外部人员、其他工具或手工 SSH 产生的上线行为。

## 准备和核验候选版本

仓库提供 `scripts/release_candidate.py` 和 `Release candidate (not deployment)` 工作流。它们只读取指定提交的 Git 对象，选择允许的应用文件，生成源码压缩包、逐文件 SHA-256 清单与产物摘要，并核验内容。打包过程不导入应用、不安装依赖、不访问 SSH、不启动服务，也不发布 GitHub Release。

本地使用时，`build` 必须指定 `--repo`、完整的 40 位小写 `--commit` 和位于所有 Git 工作区之外的 `--output-dir`。工作区里未提交的编辑不会进入候选。随后使用 `verify --archive ... --manifest ... --repo ... --commit ...`，将产物与同一提交重新比对；检查在内存中进行，不解压或执行候选代码。输出中的 `deployed: false` 表示它始终只是候选。

GitHub 的候选工作流为同仓库 PR 核对提交与集成基线；手动运行要求完整提交 SHA，并限定其属于已允许的仓库分支。工作流保留候选供审查 7 天，在运行摘要里显示提交、版本与压缩包 SHA-256。分支与触发规则以 `.github/workflows/release-candidate.yml` 为准。当前本地新增的工作流只有进入 GitHub 后才可能产生真实运行记录；没有运行记录时，观察页应保持未知或无记录。

文件白名单及敏感内容扫描会拒绝已识别的秘密模式、链接和不安全归档结构，但不能保证发现所有可能的敏感信息，公开上传前仍需审查文件范围。候选验证与 CI 是分开的证据：校验包内容通过，不代表同一提交的测试已经通过，也不代表依赖环境或研究功能已完成验收。

当前候选工作流会运行该 PR 或手动选择版本中的验证器，属于开发阶段检查，并非对恶意 PR 的独立签名或来源证明。未来生产晋级必须使用受保护、已审查的固定验证流程，对候选及同一完整提交重新核验；不能只凭任意 PR 的绿色结果上线。

## 如何理解“停止”和“回滚”

| 操作 | 当前能力与边界 |
|---|---|
| 查看工作流 | 打开真实 GitHub 运行页面核对状态和日志；页面链接本身不改变任何状态。 |
| 取消 GitHub 工作流 | 在 GitHub 中取消后，须等待 GitHub 确认。它只影响相应工作流，不能证明生产进程已经停止，更不会自动恢复旧版本。 |
| 紧急停止生产发布 | 当前未实现。后续应停止尚未开始的写入步骤，并明确显示“已请求、停止中、已停止或状态未知”。已执行的远端步骤不会因关闭网页而撤销。 |
| 回退程序版本 | 当前未实现。后续只能回退到已验证的旧候选，且需先确认与当前数据库结构兼容。 |
| 恢复数据库备份 | 当前未实现；它可能丢失备份之后的新数据，必须与程序回退分开处理，并明确恢复点与影响范围。 |

发布期间应用可能重启或失联，应用自己的页面不能保证始终提供紧急控制。生产执行器需要独立于被发布的应用，并保留独立的观察与操作入口。

## 接入生产前必须补齐的步骤

以下是后续实施与验收条件，不是已经运行的自动化流程。每一步需要产生可核对的记录，失败或未知时停止进入下一步。

1. **确认环境和授权。** 固定并核实目标主机、目录与服务身份；保留 SSH 主机密钥校验。区分开发、验证与生产环境，限制执行器权限。现有生产服务名由实际主机确认，不能直接套用安装模板里的服务名。
2. **冻结候选。** 固定仓库、完整提交 SHA、产物清单与内容摘要，确保通过 CI 的代码就是待发布的内容。后续步骤不能重新取可移动分支代替已验证候选；不得打包凭证、用户数据或未审计的旧历史。
3. **验证备份与回退点。** 在变更前核对当前版本、数据库及必要运行文件的备份是否完整、可恢复。Git bundle 不包含工作区或未跟踪文件，也不能代替数据库备份。凭证与旧历史如需保全，应受控离线保存，不能推入公开仓库。
4. **取得单写锁并预检。** 同一环境只允许一个执行器进入写入阶段。检查磁盘、权限、依赖、备份有效性、数据库迁移和旧版本兼容性；明确失败后的回退方案。当前应用启动时会初始化或调整数据库结构，程序文件切回不等于数据库已回退。
5. **隔离准备并切换。** 先在独立候选目录完成准备和检查，再采用可核对的切换方式。只允许预定目标与固定操作，不接受网页传入的任意命令、主机、路径或下载地址。
6. **核对运行结果。** 检查实际修订号与候选完全一致、基础就绪、登录及关键研究流程。真实模型、实时数据和依赖服务的验收必须有独立结果；不能用 `SELECT 1`、进程存在或 HTTP 200 代替。
7. **记录完成或恢复。** 保存操作编号、发起者、环境、候选与前一版本、每步开始/结束时间、退出结果、脱敏证据及取消确认。若失败，按已验证的兼容性决定程序回退；数据库恢复需单独确认数据影响。恢复后重新验收并记录结果。

后续控制台应展示上述实际步骤及证据，而不是估算的完成百分比。通过受控流程产生的变更可以自动追踪；若检测到清单外的程序变化，应标记为“未归属变更”，调查清楚前不能宣称发布记录完整。

## 不再作为发布入口的旧方式

不要执行 README 旧版本提到的 `/tmp/prism-deploy-p2.sh`，也不要用 `cp -r` 直接覆盖在线目录。仓库没有对这些外部脚本的内容、锁、备份与恢复结果提供保证。

`install.sh` 面向初始安装，会安装依赖、写配置并操作服务；`scripts/verify.sh` 会创建测试状态并可能调用真实模型。它们都不是只读健康检查，也不是本流程的发布执行器。旧安装模板中的服务名称与已确认生产服务可能不同，不能直接执行来“修复”当前实例。

本批 Docker 修改只修复基础健康检查。当前镜像对研究方法、CLI、运行配置和完整功能的打包与验收仍需单独验证；不要把容器的 `healthy` 当成具备全部研究功能或生产发布成功。
